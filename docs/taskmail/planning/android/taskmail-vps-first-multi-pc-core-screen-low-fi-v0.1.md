# TaskMail VPS-First 多 PC 核心页面低保真方案（v0.1）

更新时间：2026-03-25

## 状态

本文是 `VPS-first 多 PC` 主线下，Android 侧核心页面的低保真 UI companion doc。

它依附于以下文档：

- `docs/taskmail/planning/android/taskmail-vps-first-multi-pc-user-requirements-authority-v0.1.md`
- `docs/taskmail/planning/android/taskmail-vps-first-multi-pc-information-architecture-v0.1.md`
- `docs/taskmail/planning/android/taskmail-vps-first-multi-pc-viewstate-action-mapping-v0.1.md`

它不承担当前实现 truth，也不替代最终视觉稿或组件级设计规范。

本文回答的问题是：

**在进入具体视觉设计和实现前，首页、新任务页、Session 页三张核心页面的低保真结构应长什么样。**

## 目的

这份文档只冻结三类信息：

1. 页面区块顺序
2. 页面主交互
3. 关键状态变体

它不冻结：

- 最终视觉风格
- 具体颜色、排版和动画
- Compose 组件拆分细节
- 最终接口字段命名

## 低保真设计原则

在当前主线下，核心页面的低保真方案必须满足：

1. 主对象是 `session`，不是 mail thread。
2. 新任务页只负责“选目标 + 写任务 + 设执行策略”。
3. Session 页必须同时容纳“状态、直播、结果、文件、follow-up”。
4. `profile / permission` 是执行策略，不是系统权限中心。
5. “等待用户输入”的任务必须在首页和 Session 页都被抬高。
6. 页面默认语言应是用户语义，不是协议语义。

## 页面集合

当前先冻结三张核心页面：

1. 工作台首页
2. 新任务页
3. Session 详情页

结果查看和文件查看在第一轮低保真中先作为 Session 页内嵌区块处理，不单独展开成独立页面。

## 1. 工作台首页

### 页面目标

首页要让用户在 3 秒内回答三件事：

1. 现在有哪些电脑可用
2. 我有哪些任务要继续处理
3. 我要不要发起一个新任务

### 低保真结构

```text
+--------------------------------------------------+
| TaskMail                                         |
| [搜索/筛选]                          [设置/诊断] |
+--------------------------------------------------+
| [新建任务]                                       |
+--------------------------------------------------+
| 需要我处理                                       |
| ------------------------------------------------ |
| Session A | 等待我回复 | PC: Home | ws: repo_a   |
| Session B | 失败       | PC: Office | ws: repo_b |
+--------------------------------------------------+
| 进行中                                           |
| ------------------------------------------------ |
| Session C | 运行中     | PC: Home | live...      |
| Session D | 排队中     | PC: Mini | queued       |
+--------------------------------------------------+
| 最近结束                                         |
| ------------------------------------------------ |
| Session E | 已完成     | 2 files | summary...    |
+--------------------------------------------------+
| 可用电脑                                         |
| ------------------------------------------------ |
| Home PC   | online  | 3 workspaces              |
| Office PC | stale   | 2 workspaces              |
| Mini PC   | offline | 1 workspace               |
+--------------------------------------------------+
| 常用工作目录                                     |
| ------------------------------------------------ |
| repo_a / app-thunderbird                         |
| repo_b / mail_runner                             |
+--------------------------------------------------+
```

### 首页区块顺序为什么这样定

- `新建任务` 放在最上，是因为它是最常见的主动作。
- `需要我处理` 放在 `进行中` 前面，是因为 `awaiting_user_input` 比单纯 running 更需要用户立即关注。
- `可用电脑` 放在下半区，是为了给用户路由上下文，但不抢 `session` 主对象的位置。
- `常用工作目录` 保留在底部，服务于新任务入口，不应压过当前任务流。

### 首页主交互

- 点击 `新建任务` -> 进入新任务页
- 点击任一 `session` 卡片 -> 进入 Session 页
- 点击 `PC` 卡片 -> 过滤或展开其 workspace/session
- 点击 `workspace` 项 -> 带预选参数进入新任务页

### 首页关键状态变体

#### 空状态

```text
+------------------------------------------+
| TaskMail                                 |
+------------------------------------------+
| 还没有任务                               |
| [新建任务]                               |
|                                          |
| 当前可用电脑：Home PC, Office PC         |
+------------------------------------------+
```

#### 节点离线状态

```text
+------------------------------------------+
| Home PC 当前离线                         |
| 你仍可查看历史任务，但暂时不能继续发送。 |
+------------------------------------------+
```

#### 等待用户输入高亮状态

`需要我处理` 区必须在视觉层级上高于普通 `进行中` 区，不允许把 `awaiting_user_input` 埋进普通列表排序。

## 2. 新任务页

### 页面目标

新任务页的唯一目标是让用户把“在哪做什么”说清楚。

### 低保真结构

```text
+--------------------------------------------------+
| < 返回                 新建任务                   |
+--------------------------------------------------+
| 目标电脑                                          |
| [Home PC  v]                                      |
+--------------------------------------------------+
| 工作目录                                          |
| [repo_a / app-thunderbird  v]                     |
+--------------------------------------------------+
| 任务内容                                          |
| ------------------------------------------------ |
| 请在当前仓库中检查最新的 relay 协议改动...        |
|                                                  |
|                                                  |
+--------------------------------------------------+
| 高级执行设置                          [展开/收起] |
| ------------------------------------------------ |
| Backend      [Codex v]                            |
| Profile      [Strong v]                           |
| Permission   [Highest v]                          |
| Transport    [自动/默认]                          |
+--------------------------------------------------+
| [发送任务]                                        |
+--------------------------------------------------+
```

### 页面关键说明

- `PC` 和 `workspace` 是必选区块。
- 任务输入区是主视觉重心。
- `execution_policy` 默认折叠或弱化展示，不抢任务输入区。
- `backend_transport` 默认按实现细节处理，不应默认高亮。

### 新任务页主交互

- 切换 `PC` 后刷新可用 `workspace`
- 展开高级执行设置后，读取目标 `PC/workspace` 支持的 `profile / permission`
- 点击 `发送任务` 后进入提交中状态
- 收到 `accepted` 后跳转 Session 页
- 收到 `rejected` 后在原页显示用户可理解的错误

### 提交中状态

```text
+------------------------------------------+
| 正在提交任务…                            |
| 目标：Home PC / repo_a                   |
| 执行策略：Codex / Strong / Highest       |
+------------------------------------------+
```

### 被拒绝状态

```text
+------------------------------------------+
| 无法启动这次任务                         |
| 原因：当前目标不支持所选运行档位         |
| [调整执行设置]   [返回修改]              |
+------------------------------------------+
```

### 新任务页 guardrails

- 不把 `profile / permission` 设计成独立设置页入口
- 不允许用户直接输入 raw model id
- 不把“发送成功”做成终点页；应尽快进入 Session 页

## 3. Session 详情页

### 页面目标

Session 页要让用户围绕一条持续任务完成以下动作：

- 看当前状态
- 看正在发生什么
- 看最终结果
- 看文件
- 继续回复

### 低保真结构

```text
+--------------------------------------------------+
| < 返回                 Session                   |
+--------------------------------------------------+
| say hi                                           |
| Home PC · repo_a · session_023                   |
| 状态：运行中                                     |
+--------------------------------------------------+
| 当前状态                                          |
| ------------------------------------------------ |
| 正在执行...                                      |
| Backend: Codex  Profile: Strong  Permission: Hi  |
+--------------------------------------------------+
| 最近上下文                                        |
| ------------------------------------------------ |
| 上一轮：确认先做高保真稿                          |
| 最近结论：高保真预览已落地                        |
| [查看前续]                           [历史上下文]|
+--------------------------------------------------+
| 过程直播                                          |
| ------------------------------------------------ |
| assistant: 正在检查仓库结构...                   |
| system: task accepted                            |
| stderr:                                          |
| ...                                              |
+--------------------------------------------------+
| 最新结果                                          |
| ------------------------------------------------ |
| 暂无最终结果 / 或展示 summary                    |
+--------------------------------------------------+
| 文件                                              |
| ------------------------------------------------ |
| output.json                                      |
| patch.diff                                       |
+--------------------------------------------------+
| 继续这条任务                                      |
| ------------------------------------------------ |
| [输入框：补充说明 / 回复...]                     |
| [状态] [发送回复] [更多动作]                     |
+--------------------------------------------------+
```

### Session 页区块顺序为什么这样定

- 顶部先给 `session` 身份和路由上下文，避免用户忘记自己在哪条任务。
- `当前状态` 紧跟头部，先给判断。
- `最近上下文` 放在直播前，先帮用户补足继续 follow-up 所需的最小上下文。
- `过程直播` 放在中间，让用户知道它在做什么。
- `最新结果` 放在直播后，避免把中间过程误读成最终收口。
- `文件` 跟随结果区，保持“结果 -> 文件”的自然顺序。
- `follow-up` 固定在底部，是这页最重要的操作区。

### Session 页主交互

- 点击 `状态` -> 发送 `status` follow-up
- 点击 `查看前续 / 历史上下文` -> 进入按回合组织的历史层
- 输入文字并点击 `发送回复` -> 发送 `reply`
- 点击 `更多动作` -> 打开 `pause / resume / kill` 的二级菜单
- 点击文件项 -> 查看或下载文件

### Session 页关键状态变体

#### 运行中

- `当前状态` 显示 running
- `过程直播` 展开
- `最新结果` 可为空或显示“尚未结束”

#### 等待用户输入

```text
+------------------------------------------+
| 需要你的回复                             |
| 系统正在等待你补充说明后继续。           |
+------------------------------------------+
```

此时 `follow-up` 区必须视觉上更突出，且应尽量缩短“我看到状态”和“我开始回复”之间的距离。

#### 查看前续

```text
+------------------------------------------+
| 历史上下文                               |
| 最近回合（展开）                         |
| - 你：先做高保真稿                       |
| - 系统：已生成静态 HTML 预览             |
| 更早回合（折叠）                         |
| [查看完整过程]                           |
+------------------------------------------+
```

历史层按回合组织，不按 mail thread 原样堆叠。

#### 已完成

- `当前状态` 显示 done
- `最新结果` 成为主要阅读区
- `过程直播` 可折叠为次要区
- `follow-up` 仍保留，但默认语义是“继续这条任务”

#### 失败

- `当前状态` 显示 failed
- `最新结果` 里展示失败摘要
- `follow-up` 区允许用户直接补充说明后重试方向性回复

### Session 页的 `更多动作` 菜单

第一版建议做成显式二级操作，而不是主按钮并排展示：

```text
[更多动作]
  - 暂停
  - 恢复
  - 停止
  - 查看执行设置
```

这样可以避免把次要动作挤进主跟进流。

### Session 页 guardrails

- 不把时间线做成 mail-style 对话气泡主视图
- 不把完整历史默认铺满 Session 首页
- 不让 raw event 直接顶替用户态文案
- 不让直播文本覆盖结果区
- 不让用户在本页重新选 `PC / workspace`

## 响应式与滚动原则

虽然本文不展开具体视觉设计，但当前先冻结几个布局原则：

- 首页以垂直信息流为主，支持 section 折叠
- 新任务页以单列表单为主
- Session 页以单列纵向流为主，底部 follow-up 区固定或半固定
- 在手机竖屏下，不应要求用户左右切主内容

## 文案原则

核心按钮和状态文案优先使用用户语言：

- `新建任务`
- `继续这条任务`
- `查看状态`
- `需要你的回复`
- `运行中`
- `已完成`
- `失败`

避免直接把这些文案做成：

- `command_dispatch`
- `command_ack`
- `result`
- `artifact_manifest`
- `permission_modes`

这些可用于 debug 或内部日志，但不应成为主 UI 文案。

## 进入高保真设计前必须已确定的事项

在进入具体视觉设计或 Compose 组件拆分前，以下事项必须视为已冻结：

1. 首页、新任务页、Session 页是首批核心页面
2. `session` 是主对象
3. 路由选择只在新任务页发生
4. `execution_policy` 是高级执行设置
5. `event / output_chunk / result / artifact` 在 Session 页分层呈现
